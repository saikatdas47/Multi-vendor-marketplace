CommerceX — quick reference
===========================

THE DATABASE IS CALLED  commercex
It is set in exactly one place: DB_NAME in Backend/.env
Nothing else. Never type another name.

(This file used to say "appnamedb" from the very first scaffold. That name is
dead — it caused a long debugging session where Django silently connected to the
old database. If you ever see "appnamedb" anywhere again, it is stale.)


--- start postgres -----------------------------------------------------------

brew services start postgresql@15
brew services list


--- first-time database setup ------------------------------------------------

createdb commercex

# only if the postgres role doesn't exist yet:
psql postgres -c "CREATE ROLE postgres WITH LOGIN PASSWORD 'admin';"
psql postgres -c "ALTER ROLE postgres WITH SUPERUSER CREATEDB CREATEROLE;"

psql postgres -c "\l"        # list databases
psql postgres -c "\du"       # list roles


--- backend: ONE COMMAND -----------------------------------------------------

cd Backend
./setup.sh

Does everything: venv, dependencies, .env repair, postgres role + database,
migrations, demo data. Safe to run again any time.

Then to run the server:

source venv/bin/activate          # then use `python`, NOT `python3`
python manage.py runserver        # http://127.0.0.1:8000


DO NOT run: cp .env.example .env
.env holds your real SECRET_KEY and DB_PASSWORD. Copying over it blanks both
and Django refuses to start. setup.sh handles this correctly.


--- frontend -----------------------------------------------------------------

cd Frontend/vite-project
npm install
npm run dev                       # http://localhost:5173

npm run lint:all                  # oxlint + contrast checks + their tests
npm run lint:contrast             # WCAG AA check on every bg/text pair, both themes
npm run lint:contrast -- --verbose  # print every pair and its ratio
npm run test:contrast             # prove the contrast checker still catches bugs


--- the contrast rule --------------------------------------------------------

Light background => dark text. Dark background => light text. In BOTH themes.

Components reference semantic tokens (surface, fg, fg-muted, line, …), never
raw palette colours, because a semantic token has a light value and a dark
value and a raw one does not. `text-brand-700` reads fine on a white card and
is unreadable on the dark one.

lint:contrast resolves every utility to a real hex value twice — once with
@theme, once with .dark applied — walks the JSX tree to find the background
each element actually sits on, and computes the WCAG ratio. It is not a
name-matching regex, so it catches pairs that look correct and aren't.

If a finding is genuinely intentional, put the reason above the element:

    {/* contrast-ok: gold rating fill, 1.6:1 by convention */}
    <Star className="text-accent-400" />

Suppressions are printed on every passing run, so they can't accumulate
unnoticed. There are currently 2, both for gold star ratings.


--- which database am I actually on? -----------------------------------------

python manage.py shell -c "from django.db import connection; print(connection.settings_dict['NAME'])"
# must print: commercex

If it prints anything else, Backend/.env is missing or DB_NAME is wrong.
Fix it in .env — never in settings.py.


--- start completely fresh ---------------------------------------------------

psql postgres -c "DROP DATABASE IF EXISTS commercex WITH (FORCE);"
psql postgres -c "CREATE DATABASE commercex;"
python manage.py migrate && python manage.py seed_demo

--- gotchas that already bit us ----------------------------------------------

1. Backend/.env holds ONLY  KEY=value  lines. Shell commands pasted into it are
   ignored, and one of them (a CREATE DATABASE appnamedb line) sat there
   silently. settings.py now refuses to start if .env is missing.

2. `cp .env.example .env` wipes DB_PASSWORD and SECRET_KEY. It has bitten this
   project twice. Only run it if Backend/.env genuinely does not exist, and
   regenerate SECRET_KEY straight afterwards (see Backend/README.md).

3. Inside an active venv, `python3` can resolve to Homebrew's Python outside the
   venv, where Django isn't installed. Use `python`.

4. Tests build their own throwaway database, so `manage.py test` passing does
   NOT prove your dev database is migrated. Check with the shell command above.

5. macOS filesystems are CASE-INSENSITIVE. Typing `cd Backend` while already
   inside Backend/ lands you in Backend/backend/ (Django's settings package),
   because it matches `backend` case-insensitively. zsh shows the casing you
   TYPED, so the prompt still reads "Backend" and lies to you. The symptom is:

     can't open file '.../Backend/backend/manage.py'   <- note the two levels

   Check where you really are with:  pwd -P
   Fix:  cd "/Users/saikatdas/Desktop/Project/Simple Project/Backend"
